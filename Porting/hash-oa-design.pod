=head1 NAME

hash-oa-design - Experimental hash storage with open addressing

=head1 STATUS

This document records the design and compatibility questions for the
experimental open-addressed hash representation. It is not a promise that
every Perl hash uses this representation.

=head1 REPRESENTATION

Empty ordinary hashes allocate no entry storage, and C<keys> or C<each> on an
empty hash does not allocate it. With a positive linear threshold, a
one-entry hash uses an arena-backed compact C<HE> slot with no chain pointer.
With two or more entries, very small hashes can use a dense array of compact
C<HE> entries and linear search without
allocating open-addressing metadata. The startup
environment variable C<PERL_HASH_LINEAR_MAX> selects the maximum number of
entries kept in this form. The default is four. Zero disables this form and
uses indexed storage from the first key. Positive settings of two, four, or
eight select the corresponding threshold. With a positive threshold, adding
a second key moves the singleton into a compact entry array, which grows
through capacities two, four, and eight as needed. Deletion shifts later
entries left to keep the array dense. Inserting beyond the selected threshold
promotes the same entries into the indexed form. With a positive threshold,
deleting from two entries to one returns to the arena-backed singleton
representation. Deleting the last entry or clearing the hash returns it to
the unallocated state.

After promotion, the hash uses an open-addressed index separate from the
contiguous array of entries. Each index slot stores only an entry identifier.
The full cached hash remains in the entry's C<HEK>. The identifier uses one
byte when slot capacity is at most 128, two bytes when it is at most 32,768,
and four bytes above that. Zero means empty; an all-ones identifier marks a
deleted slot; live identifiers are entry positions plus one. The entry array
grows independently, by about 1.2 times its current capacity. On a colliding
insert, the slot array is maintained when projected occupancy reaches about
two-thirds. If tombstones are at least half of the currently occupied slots
(tombstones are at least as numerous as live entries), the index is rebuilt
at the same capacity; otherwise it doubles. This is a target, not a hard
occupancy ceiling: an insertion that does not collide can take the table
above two-thirds. Deleted entries join a
freelist whose link is encoded as an integer, allowing the entry allocation
to be reused without storing a pointer in every entry.

With the default positive threshold, a singleton uses one arena-backed
16-byte compact C<HE> on 64-bit builds. At threshold zero, the first key uses
indexed storage instead. Including the common 24-byte C<HV> and 32-byte
C<XPVHV>, the default singleton's structural total is 72 bytes. The promoted
open-addressed form has 24 bytes of metadata
before the entry-identifier array in the same allocation. Its index slots use
one, two, or four bytes as the identifier widens. The linear form has no
index allocation or metadata header. This design does not enlarge the C<HV>
or C<XPVHV> structure. The original chained representation used a 24-byte
C<HE> on 64-bit builds; these sizes depend on pointer width.

This separates probe-table growth from entry growth. It avoids moving live
entry records when the slot table expands and keeps the per-slot index small.
The trade-off is that a lookup follows an index identifier to an entry and
then reaches its C<HEK> to check the cached hash and key. Deletion and
iteration must maintain entry allocation and slot state together.

=head1 API AND ABI COMPATIBILITY

The Perl-level hash behavior remains the compatibility target: key identity,
iteration, deletion, tied magic, restricted keys, and value lifetime must
continue to follow existing rules.

The C API exposes more than Perl-level behavior. C<hv_fetch()> and related
functions return an C<SV **> that points to a value field. That field is
inside the entry record. Growing the contiguous entry array relocates that
record and invalidates a previously returned C<SV **>. In the optional
headerless linear mode, deletion shifts later records and invalidates their
pointers too. Reacquire returned C<HE *> and C<SV **> pointers after these
mutations. XS code that saved such a pointer across growth or deletion may
need changes. Perl-level lvalue references do not have the same problem
because they refer to the value SV, not its slot.

The C<HE *> interface is more sensitive. Public macros such as C<HeVAL()> and
C<HeKEY()> expose entry fields, and hash iteration APIs can expose entries to
XS code. Code that saves an C<HE *> across mutation may depend on a stable
address. A compact entry in a relocatable array cannot provide that stability
by itself; reacquire it after entry-array growth or deletion from linear
storage. The tied-fetch pool uses a standalone 16-byte arena C<HE>; when
retired, its link is stored in the value union. C<PL_strtab> contains no
C<HE> records: its open-addressed slots point directly to individually
allocated shared C<HEK>s. Each shared-key allocation has a reference-count
prefix, and the C<HEK> address remains stable while referenced, including
when the slot array grows.

C<HeNEXT()> was a public macro for following chained entries. Ordinary hash
entries have no chain link, and the macro has no hash argument that can
identify the entry kind. The macro is therefore removed. C<PL_strtab> no
longer stores chain-linked C<HE>s, so C<HeSHARED_NEXT()> is removed too.
This is a source compatibility change for XS code that used either macro.
New code should use the hash-aware entry index macros
C<HvENTRY_LIMIT()>, C<HvENTRY_FIRST()>, and C<HvENTRY_NEXT()>, or the
iterator APIs.

C<HvMAX(hv)> is no longer an lvalue. XS code that wrote it must use
C<HvMAX_SET(hv, max)> for indexed storage or
C<HvMAX_SET_LINEAR(hv, capacity)> for headerless linear storage. The raw
C<xhv_max> field contains the linear-mode tag and must not be written
directly. C<HvIS_OA(hv)> identifies the compact non-strtab hash family,
including headerless linear hashes; C<Hash::Util::hash_storage_info()> uses
C<open_addressed> for actual index allocation and C<linear> for the
headerless form.

The shared-key table starts with 32,768 pointer slots. On a colliding
insertion, it checks whether projected occupancy reaches two-thirds.
Non-colliding insertions can take occupancy above that target. When tombstones
are at least as numerous as live entries, it rebuilds at the same capacity;
otherwise it doubles. An interned C<HEK> is canonical for its key bytes and
storage flags, and its address remains stable while referenced, including
across slot-array growth.
C<share_hek()> increments the shared reference count; C<unshare_hek()>
releases it, and the address becomes invalid when the final reference is
released. There is no value
slot or C<HE *> to fetch from C<PL_strtab>; generic hash-entry access and
iteration APIs must not be used on it. Hash::Util provides
C<shared_key_refcount()> and C<shared_keys()> for functional inspection;
its bucket diagnostics do not expose C<PL_strtab>.
C<immortalize_key()> acquires one interpreter-lifetime reference per call.
A sparse list records counts only for pinned keys, so full destruction can
release intentional pins before checking for unbalanced owners. The list
is copied into cloned interpreters; ordinary shared HEKs need no extra
per-key metadata. On a typical 64-bit build, the pin registry adds an
eight-byte pointer to the table header and a 24-byte record per distinct
pinned key. Pin registration scans this sparse list; ordinary interning
does not scan it. A larger pin workload may justify indexing the registry.

Any change to C<HE>, C<HV>, or the C<hv_fetch()> contract can affect XS and
embedding code even when Perl-level tests pass. Review generated API
documentation, existing extensions, and the source compatibility surface
before treating the experiment as a settled ABI.

=head1 VALIDATION

F<t/op/hash-oa.t> covers repeated insert/delete reuse, binary and UTF-8 keys,
iteration while deleting, restricted hashes, tied hashes, destructor
reentrancy during replace/delete/clear, lvalue references retained through
growth, optional thread cloning, independent index and entry growth, free-list
reuse, and tombstone rebuilding. The focused XS hash tests also exercise
collision-triggered growth using keys selected by their computed homes. The
shared-key tests cover canonical interning, reference counts, UTF-8 flags,
tombstone reuse, stable C<HEK *> identity through table growth, and thread
cloning. XS::APItest-only diagnostics scan the HEK-pointer slots before
constructing their result; Hash::Util does not expose the table layout.

F<Porting/bench-hash-oa.pl> runs each workload in a fresh process and reports
CSV fields for interpreter version, operation, size, repetitions, operations,
elapsed seconds, seconds per batch, seconds per operation, peak resident
memory in KiB where Linux procfs is available, and final key count. Small and
medium sizes target about 100,000 operations. The one-million-entry workloads
use three batches. Each batch is measured separately, with input table setup
outside the timed region. A group shares one timer across up to about 100
entries, limiting clock-call overhead for small hashes while keeping temporary
hashes small. Per-operation times include Perl loop and key-access overhead.
Churn counts a delete and an insert as two operations. The high-hole workload
deletes 90 percent of a populated table. The keys/values/each high-hole cases
delete before timing and divide iteration time by the remaining live entries.
Tombstone churn repeatedly replaces all live keys while retaining the same
live count. Both current RSS and peak RSS are recorded, showing the process
footprint after deletion beside its high-water mark.

When C<Hash::Util::hash_storage_info()> is available, the CSV includes live
entries, index and entry capacities, tombstones, entry and freelist usage,
probe counts, requested bytes, and allocator bytes. The baseline requested
byte count includes live C<HE> records and the bucket array, but excludes
arena slack. Its allocator-bytes field is zero because the baseline chained
C<HE> records come from Perl's shared HE arena. The open-addressed allocator
count uses glibc C<malloc_usable_size()> for both the index allocation,
including its metadata
header and slots, and the entry allocation. Its requested-byte fields break
out metadata, index, and entry storage. Process RSS includes benchmark keys
and values, plus the small number of hashes in the current timing group. Read
it separately from table
allocation figures. The traversal cases measure C<keys>, C<values>, and
C<each> separately. Insert timings cover all entries in a fresh hash and
include any table growth; the separate growth-event workloads time a single
index or entry-capacity transition. The legacy build reports entry-vector
growth as unsupported because it has no separately growing vector.

In the tiny form, including empty and singleton hashes, C<linear> is true and
C<open_addressed> is false.
Index capacity, index allocation, hash storage, tombstones, freelist, and
probe counts are zero. Entry bytes and requested bytes describe only the
dense HE array; C<entry_used> is the live count and C<entry_spare> is the
remaining capacity. Promotion switches these fields to indexed storage.
The singleton state is reported separately by C<arena_backed>; its entry
bytes describe the compact HE arena slot, with C<arena_slot_size> equal to
C<he_size>. An empty hash reports zero entry bytes
and a null entry address, including after C<keys>, C<each>, or C<clear>.

F<Porting/bench-hash-oa-compare.py> runs baseline and candidate workers in
paired trials, uses the same deterministic C<PERL_HASH_SEED> in each pair,
randomizes which interpreter runs first, and writes raw CSV, a JSON summary,
and JSON metadata. Metadata records the Perl executable digest, source
revision and dirty state, compiler/configuration flags, CPU, kernel, input
sizes, trial count, driver seed, worker/driver digests, and source diffs
where a Git source tree is available. An archived build without Git metadata
is identified by binary digest and marked as lacking a source diff. Each
run also records the selected candidate C<PERL_HASH_LINEAR_MAX> value. Each
paired trial uses a common hash seed and a
separate query seed; run order is randomized. The random-hit
case shuffles its query keys before timing. Default sizes include every size
from 1 through 32 plus 128, 1,000, 10,000, 100,000, and 1,000,000. Use
C<--sizes> and C<--workloads> to select a smaller run. For example:

  python3 Porting/bench-hash-oa-compare.py \
    --baseline /path/to/original/perl \
    --candidate /path/to/oa/perl \
    --outputdir /path/to/results

Use C<--linear-max 0>, C<--linear-max 2>, C<--linear-max 4>, or
C<--linear-max 8> to set C<PERL_HASH_LINEAR_MAX> for the candidate process.
The driver unsets this variable for the baseline. The selected mode is
recorded in the output metadata and raw CSV.

Summary speedup is baseline nanoseconds per operation divided by candidate
nanoseconds per operation, so values above one favor the candidate. It gives
the median and observed minimum/maximum across paired trials. Growth-event
rows report the start live count for every timed sample and the before/after
capacity transitions. A speed ratio is included only when both builds
measure all samples at the same live counts. Memory summaries include
requested bytes and peak RSS per live entry, along
with allocator bytes per live entry; candidate allocator bytes sum
C<malloc_usable_size()> for index and entry allocations where available.
The baseline allocator count is zero because its hash entries are arena
cells, not standalone allocations. Process RSS includes Perl, keys, values,
and setup; RSS per live entry is dominated by interpreter and input
overhead at small table sizes. Use the requested-allocation fields to compare
hash storage directly. Per-operation
timings still include Perl loop and key-access overhead. Results are specific
to the recorded host and build and do not establish performance on other
platforms or workloads.

=head2 Shared-key pointer index measurements

The shared-key comparison on 2026-11-01 used x86-64 Linux on an Intel
Core i7-1185G7. Both builds already used compact ordinary hashes; this
comparison measures the chained versus pointer-index shared string table,
not the whole ordinary-hash representation change. Five paired trials used
a fixed hash seed. CPU frequency was not pinned.

F<Porting/bench-strtab.pl> and F<Porting/bench-strtab-compare.py> reproduce
the controlled fill/clear workloads. Each round fills a normal hash with
computed string keys and then undefines it. The shared string table retains
its capacity between rounds; the ordinary hash releases its arrays. The
second-owner workload retains the keys in a separate keeper hash, so clearing
the target does not release the final key references. Keeper setup and
teardown are outside that measurement.

The table reports median full-cycle time, after averaging each trial's
rounds: 20 rounds at 100,000 keys and five at one million. Units are
milliseconds per fill/clear cycle. Stage medians are not added together.

  Keys       Ownership     Chained strtab   Pointer OA
    100,000  Final owner          33.84          34.32
  1,000,000  Final owner         608.8          613.7
    100,000  Second owner         26.03          25.64
  1,000,000  Second owner        462.5          458.7

These full-cycle results are close to parity, with differences around one
percent. Repeated final-owner fills are slower with the pointer index, while
repeated clears are faster; the costs largely offset each other. First
clears behave differently from later clears. At 100,000 keys their median
cost was 65.1 ns/key for chaining and 77.2 ns/key for OA. At one million it
was 158.6 and 163.6 ns/key. These timings should not be generalized across
allocators or key distributions.

Native CPU samples and per-round Callgrind profiles locate the first-clear
penalty in allocator cleanup when freeing the ordinary hash index after its
entries. In separate fresh-process snapshots, the chained baseline's index
was allocated with mmap, while the candidate's same-sized index was an
arena allocation. Unmapping the former avoids the allocator consolidation
that freeing the latter triggers. Later rounds use arena allocations in both
builds. Requested sizes and capacities matched. This is an allocation-history
effect, not evidence that the final-key probe is slower. Restoring the old
HEK allocation request size by adding temporary padding did not improve the
candidate's full clear, so key allocation size alone does not explain the
allocation history.

A temporary XS helper separately timed the C key-release API after warming
the table, excluding ordinary HE and SV destruction. With 24-byte keys,
final-reference release medians were 18.80 versus 16.26 ns/key at 100,000
keys, and 55.51 versus 47.49 ns/key at one million. Pointer-only probes and
removal without freeing were close to parity. These measurements isolate
mechanisms and do not replace full-cycle benchmarks.

On this 64-bit build the shared allocation prefix falls from 24 bytes to
eight bytes, saving 16 requested bytes per key before allocator rounding.
The HEK header, key bytes and flags are common to both layouts. At about
102,450 total interned keys, both tables allocate 262,144 pointer slots, so
the prefix saving is about 1.56 MiB. At about 3,450 interned keys, the new
32,768-slot reservation exceeds the baseline's 8,192 slots by about 192 KiB.
After accounting for the prefix saving, the candidate uses about 138 KiB
more requested storage at that size. These estimates exclude allocator
metadata and slack. Freshly filled process RSS in the controlled final-owner
workload was 33.1 versus 31.5 MiB at 100,000 keys, and 207.6 versus 192.9 MiB
at one million. RSS includes the interpreter, keys, values and ordinary hash
storage, and allocator retention changes it on later rounds.

=head1 LIMITS AND FOLLOW-UP

The process-wide C<PL_strtab> is an open-addressed array of shared C<HEK *>
slots. It starts with 32,768 slots, stores full hashes in each shared C<HEK>,
and has no C<HE> records, entry array, or freelist. Ordinary hash entry
identifiers use adaptive one-, two-, or four-byte widths; the slot
index is limited to 2^26 slots. Deleted entries
are reused, but the entry vector does not shrink or compact after heavy
deletion; iteration therefore scans up to its historical high-water mark.
With the default C<PERL_HASH_LINEAR_MAX=4>, hashes with up to four entries
avoid the index allocation but use linear lookup and shift entries on
deletion. Setting the threshold to zero disables linear storage and uses an

replacement also pay for key-copy and

64-bit inline-hash comparison showed substantial lookup and iteration gains

The historical measurements are for 64-bit builds. On a 32-bit build, the
legacy representation uses a 12-byte C<HE> and 4-byte bucket pointer, while
the compact entry is 8 bytes. The current adaptive index adds one, two, or
four bytes per slot, depending on identifier width. The 64-bit measurements
do not imply a 32-bit memory win.
The shared C<HEK> layout retains the legacy key offset.

XS code must not retain C<HE *> or C<SV **> addresses across a hash growth.
The original chained implementation's HE arena has shared allocation slack
that cannot be attributed to one hash by the current diagnostics. It also
retains freed arena cells, so
the baseline live-cell estimate is a lower bound on retained memory after
deletion; compare current process RSS for that case. Candidate allocator
bytes report usable capacity for the index and entry allocations, but exclude
allocator metadata stored outside those blocks.

C<Cpanel::JSON::XS> canonical encoding is a concrete compatibility case.
When C<TO_JSON> callbacks run during encoding, they can mutate and grow the
source hash while the encoder is using its entries. The encoder now snapshots
the original entries into standalone C<HE>/C<HEK> records and retains the
key/value SVs before calling callbacks. This preserves the original canonical
key/value set across reentrant mutation and avoids retaining pointers into a
relocating entry array. The snapshot adds per-entry allocation, key-copy, and
reference-counting costs to canonical encoding; the regression test exercises
mutation, growth, and callback exceptions.
